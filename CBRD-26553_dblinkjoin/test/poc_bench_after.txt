========================================
Before / After 비교 및 리뷰
========================================

  POC-A (고선택도, 0.01%)
    Before: 0.491200 sec
    After:  0.018400 sec
    배율:   26.7x 빠름  ★★★★★

    리뷰:
      100,000행 전체 fetch → 10행만 fetch 로 전환.
      전송량 1/10,000 감소가 실행 시간에 그대로 반영.
      push-down 최적화의 핵심 효과 확인.

  POC-B (제로 매칭)
    Before: 0.481200 sec
    After:  0.019600 sec
    배율:   24.5x 빠름  ★★★★★

    리뷰:
      Before는 매칭이 없어도 100k행 전체 fetch 후 로컬 filter.
      After는 10회 execute × 0행 반환 → fetch 자체 없음.
      zero-match 케이스에서 효과가 가장 압도적.

  POC-C (100% 매칭)
    Before: 0.023200 sec
    After:  0.094800 sec
    배율:   4.1x 느림  ✗

    리뷰:
      Before: 1회 execute, 1,000행 fetch → 로컬 hash join.
      After:  100회 execute × 100행 fetch = 10,000행 fetch.
        전송량 10배 + execute 100배 → 예상대로 역효과.
      MEMOIZE hit 90% 효과가 사라진 것도 원인 중 하나.
      cost 기반 push-down 적용 여부 판단이 필요한 케이스.

  POC-D (outer 많음, remote 작음)
    Before: 0.017200 sec
    After:  0.272000 sec
    배율:   15.8x 느림  ✗

    리뷰:
      Before: 1회 execute, 5행 fetch → 이미 최소 비용.
      After:  1,000회 execute × ~0행 fetch → round-trip이 지배적.
        실측 execute당 약 0.27ms (0.272s / 1,000회).
      remote가 작고 outer가 많을 때 최악의 케이스 확인.
      WAN 환경에서는 latency 배율만큼 더 악화될 것.

  POC-E (손익분기, 전송행 동일)
    Before: 0.227600 sec
    After:  0.480800 sec
    배율:   2.1x 느림  ✗

    리뷰:
      전송행 수는 동일 (100,000행)한데 After가 2.1배 느림.
      After: 10회 execute × 10,000행 → execute당 약 48ms.
      Before: 1회 execute × 100,000행 → 약 228ms.
        → 동일한 데이터를 10번에 나눠 보내면 오히려 비쌈.
      예상(유사하거나 약간 느림)보다 더 느린 이유:
        execute 1회의 setup 비용 자체가 무시 못 할 수준.
      핵심 통찰: 실제 break-even 지점은 전송행 동일 지점보다
        훨씬 낮다 → After가 유리하려면 전송량을 크게 줄여야 함.

========================================
종합 결론
========================================

  최적화 효과 확인 (After 승):
    POC-A: 26.7x 향상 — 낮은 선택도에서 압도적 효과
    POC-B: 24.5x 향상 — zero-match에서 가장 극적인 개선

  역효과 확인 (Before 승):
    POC-C:  4.1x 악화 — remote 전체가 매칭될 때
    POC-D: 15.8x 악화 — remote 작고 outer 많을 때
    POC-E:  2.1x 악화 — 전송행 동일해도 round-trip 비용 발생

  Phase 1 결론:
    push-down 자체는 정상 동작.
    선택도가 낮은 케이스(A, B)에서 효과 명확히 입증.
    선택도가 높거나 outer가 많은 케이스(C, D, E)에서 역효과.
    → Phase 2 과제: cost 기반으로 push-down 적용 여부 판단 필요.
       기준: remote_cardinality × join_selectivity 가 임계값 이하일 때만 적용.
