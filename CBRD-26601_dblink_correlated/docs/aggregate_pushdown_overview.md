## 1. 작업 개요

### 1.1 성격

**집계 함수 push-down**은 특정 기능에 한정된 것이 아니라, 서브쿼리·조인·파티션 등에서 **집계를 가능한 한 데이터 가까운 쪽(아래쪽)**으로 내리는 **공통 최적화**이다. 이 최적화를 도입하면, **dblink를 포함한 다양한 실행 단위들이** “더 적은 데이터로 상위 계층에 값을 전달”하는 이득을 함께 얻는다.

### 1.2 목표

**집계**(COUNT, MIN, MAX, SUM 등)를 **내부(서브쿼리·원격 등)** 에서 수행하도록 push하여, 바깥에서는 **집계 결과 1건만** 받도록 한다. 로컬에서 “여러 행 수신 후 집계”하는 대신, 내부에서 집계한 **값 하나**만 받는 것이 목적이다.

### 1.3 한 줄 요약

**내부에서 여러 행 반환 후 로컬에서 집계** → **내부 실행을 `SELECT agg(...) FROM ...` 형태로 바꿔 내부에서 집계·1행만 반환**.

### 1.4 적용 대상(혜택을 보는 곳)

| 대상 | 내용 |
|------|------|
| **일반 서브쿼리 / 조인** | 바깥에서 SUM 등 할 때, 안쪽 서브쿼리에서 먼저 집계해 행 수를 줄인 뒤 전달. |
| **파티션 단위 처리** | 파티션별로 집계 후 상위에서 합산 → I/O 및 중간 데이터 감소. |
| **원격/외부 소스 (dblink 등)** | 원격/외부 소스에 전달하는 쿼리를 `SELECT agg(...) FROM ... WHERE ...` 형태로 구성해, 원격에서 집계 값 1건만 반환받을 수 있다. |

### 1.5 적용 시 “현재 vs 개선 후” 예 (외부 소스)

| 구분 | 현재 | 개선 후 |
|------|------|---------|
| 외부로 전달되는 SQL | `SELECT col, ... FROM remote_t` (집계 없음) | `SELECT COUNT(*) FROM remote_t WHERE ...` 등 |
| 전송 | 여러 행(또는 전체) | **1행 1값** (집계 결과) |
| 로컬 | 수신 행에 대해 집계 수행 | 수신한 1행만 사용(집계 불필요) |

## 2. 필요한 이유

### 2.1 현재 제약

- `pt_copypush_terms()`(CUBRID의 일반 push-down 경로)는 **WHERE 절 term**만 대상으로 복사·추가한다. **SELECT 절의 집계**는 term_list에 포함되지 않으므로, 이 경로로는 집계를 내부로 넘길 수 없다.
- `pt_check_pushable_term()`에서 **집계가 있는 서브쿼리**로 correlated term을 push하면 `is_correlated_with_agg`로 **차단**한다. 이는 correlated term push의 일반 경로에 적용되는 제약이다.
- 이 두 제약은 derived subquery·dblink 등 내부 실행 단위에 공통으로 작용하며, 결과적으로 **집계를 내부로 넘기는 경로가 없다**. 어떤 내부 실행 단위(일반 서브쿼리, 외부 소스 등)에서도 “행 스캔 후 로컬에서 집계”하는 구조만 존재한다.

### 2.2 기대 효과

- **일반 서브쿼리·조인·파티션**: 내부에서 집계해 1행만 전달 → 중간 데이터량·로컬 집계 비용 감소.
- **원격/외부 소스**: 집계를 외부로 push하면 그쪽에서 집계 1건만 계산·전송 → 네트워크 전송량과 로컬 집계 비용을 크게 줄일 수 있다.
- 리포팅·대시보드 등 “집계 값 하나”를 스칼라 서브쿼리로 가져오는 패턴 전반에서 효과가 있다.

### 2.3 독립성

- **dblink correlated 조건 push-down·LIMIT push-down과 별개 작업**. 집계 push-down은 “내부 실행을 집계 쿼리로 재구성”하는 별도 설계가 필요하며, 단독 이슈로 진행 가능.

## 3. 작업 내용

### 3.1 난이도

**상**. 서브쿼리 **형태 인지**(단일 집계 패턴), **내부 실행/SQL 재구성**(SELECT 리스트가 집계식으로 변경), **반환 형태**(1행 1값) 처리, 집계 종류·원격 호환성(외부 소스 시) 등 검토할 항목이 많음.

### 3.2 작업 범위

| 구분 | 내용 |
|------|------|
| **공통** | 서브쿼리가 “단일 집계 한 개” 패턴인지 판별 (1차 대상: SELECT 리스트가 집계식 단 하나인 경우; `SELECT COUNT(*), MAX(id)` 등 다중 집계나 `SELECT COUNT(*) + 1` 등 집계 포함 표현식은 추후 검토). 내부 실행 계획 또는 SQL을 **SELECT agg(...) FROM ...** 형태로 재구성. 반환을 1행 1값으로 소비하는 경로. |
| **외부 소스 적용 예** | 예를 들어 dblink와 같은 원격 소스의 경우, 이 패턴을 인지해 전달 SQL을 `SELECT agg(expr) FROM remote_t WHERE ...` 형식으로 생성하고, 결과 1행 1컬럼을 단일 값으로 소비하는 경로를 사용한다. |
| **영역** | 뷰 변환 또는 XASL 생성. dblink가 아닌 일반 서브쿼리 집계 push-down도 같은 개념으로 확장 가능. |

### 3.3 예외·검토 사항

- **지원 집계**: COUNT, MIN, MAX, SUM, AVG 등. 외부 소스인 경우 원격 DB와의 문법·동작 호환.
- **GROUP BY**: 여러 그룹 반환 시 “스칼라 1값” 가정이 깨짐 → 1차는 단일 집계(그룹 없음)만 대상으로 제한 가능.
- **HAVING**: 내부 SQL에 포함 여부 및 제한.
- **빈 결과(0행) 처리**: GROUP BY 없는 집계는 매칭 행이 없어도 1행을 반환하지만 값이 달라진다(`COUNT(*)` → 0, `MIN()`/`MAX()` → NULL). 내부에서 집계 1건을 받아 소비하는 경로에서 이 케이스(0 또는 NULL)를 올바르게 처리하는지 확인 필요.
